# Figma design system: export the prototype as a Figma design system (side panel + one ⌘V)

**Made by Sebastian** (Sebastian Soong Wei)

Turns a rendered HTML prototype into Figma's **own clipboard format**. The person clicks Copy in the side panel, clicks the Figma canvas and presses ⌘V. No plugin, no MCP, no Figma API; edit access to the target file is enough.

| Output | What pastes | Use for |
|---|---|---|
| **Design page** | A "Universal Components" section (variant sets used in 2+ groups) + one section per module or flow (its screens + its own components). Every repeated element on a screen is a linked **instance** with overrides. | The hand-off file |
| **Plain copy** | Frames with auto layout, text, vectors, images. No components. | Quick checks, one-screen fixes |

## How to apply it (do these in order)

### Step 0 — Find SKILL_DIR (the engine) before anything else
1. Use the skill's base directory if the host gave one (Claude Code prints "Base directory for this skill"). Otherwise try, in order: `~/.claude/skills/dd-figma-components-sebastian/`, `<project>/.claude/skills/dd-figma-components-sebastian/`, `/mnt/skills/user/dd-figma-components-sebastian/` (claude.ai), then search: `find . ~ /mnt -maxdepth 6 -name figma-native.js -path '*engine*' 2>/dev/null | head`.
2. **Attached zip** (no skill install): if `find . ~/Downloads /mnt -maxdepth 4 -name 'dd-figma-components-sebastian*.zip' 2>/dev/null` finds the zip, unzip it into a writable scratch/temp folder and use `<that folder>/dd-figma-components-sebastian/` as SKILL_DIR. Don't unzip into the project.
3. It is the right folder when `SKILL_DIR/engine/figma-native.js` and `SKILL_DIR/engine/figma-panel.js` exist.
4. The project may already carry the engine from an earlier run (`figma/figma-native.js` or similar). Then SKILL_DIR is only needed for `tools/`; keep the project's copy unless the person asks for an update.
5. **If neither exists, stop.** Never rewrite the engine from memory or from this file: it is ~260 KB of exact code. Tell the person, once: *"This skill needs its full folder (engine + tools), not only SKILL.md. Install `dd-figma-components-sebastian.zip` as described in its README.md, or attach/upload the folder, then ask again."*

### Step 1 — Find the prototype and its screens
- The target is a **static HTML prototype**: one `index.html`, several HTML files, or a `src/` + build script that produces one. It must open in Chrome from disk.
- Look for an existing screen registry (`SCREENS`, a router table, a list of pages). The panel needs **one registry** in the §1 shape. If none exists, build it:
  - Screens written as JS templates → `render: () => html`.
  - Screens written as HTML → wrap each in `<template id="scr-…">` in one page and use `template: '#scr-…'`.
  - Separate HTML files → move each screen's markup into a `<template>` (file:// blocks `fetch`, so pages can't be loaded at run time).
- If the project already has its own viewer, ask whether to replace it with the panel or keep it and wire its buttons to `FigmaPanel.copyPage(btn)` / `copyGroup(key, btn)` / `copyScreen(id, btn)` with `panel: false`.

### Step 2 — Ask the pre-flight questions (§0.1)
Check the project's `CLAUDE.md` first: if the answers are there, don't ask again (ask again only if the scope changed). Otherwise ask Q1–Q5 as multiple-choice questions, one at a time if a question tool is available, recommended option first. Save the answers in a table in the project's `CLAUDE.md`.

### Step 3 — Install the engine
1. Copy into the project, e.g. a `figma/` folder: `engine/figma-assets.js`, `engine/figma-export.js`, `engine/figma-native.js`, `engine/figma-panel.js` (`cp SKILL_DIR/engine/*.js figma/`). The project then carries its own engine: teammates who open the prototype need neither the skill nor Claude to use the panel. Never link to SKILL_DIR from the project's HTML.
2. Copy `templates/figma.config.js` next to them and set: `name`, `storageKey` (unique), `frameWidth`, and the Q1/Q3/Q4 answers (`organise`, `copy`, `output`). Adjust `components`, `containers`, `variantProps` as the markup grows (§0.2).
3. Load order, after the project's own scripts that define the registry:
   ```html
   <script src="figma/figma.config.js"></script>
   <script src="figma/figma-assets.js"></script>
   <script src="figma/figma-export.js"></script>
   <script src="figma/figma-native.js"></script>
   <script src="figma/figma-panel.js"></script>
   ```
   Build-script projects: add the five files to the concatenation list in this order instead (a build that already inlines an `ASSETS.figmaSchema` may skip `figma-assets.js`).
4. The panel mounts itself on load: a stage that renders the current screen, a **SCREENS** handle on the left, the drawer with the screen index and copy buttons. `\` opens/closes, ← → step through screens, `data-go="<screen id>"` on any element in a screen navigates.

### Step 4 — Make the fonts and images travel
- **Fonts**: inline every family the screens use as base64 TTF `@font-face`: `python3 -I SKILL_DIR/tools/inline-fonts.py --family "Inter" path/to/static/Inter-*.ttf --js > figma/fonts.js`, then `<script src="figma/fonts.js"></script>` in `<head>`. Never load font CSS with `<link rel="stylesheet">`: from `file://` Chrome treats a linked sheet as cross-origin and the glyph reader can't read it (the same goes for Google Fonts links). Without `--js` the script prints plain CSS for a `<style>` block or a build step. Static TrueType only: it refuses variable fonts and CFF `.otf`/`.woff2`.
- If only some weights are inlined (e.g. 400 and 700), CSS 600 renders as the 700 face; the Figma style follows the face that renders (`styleFromFaces`), so Figma never asks for a style the family doesn't have.
- Add `button, input, textarea, select { font-family: inherit; }` (Chrome uses Arial otherwise, and Figma gets Arial).
- If Figma's style names for the family differ from Thin…Black (check the font picker), set `fontStyles` in the config.
- **Images**: `data:` URLs or same-folder files that load from disk. Remote images may be blocked and won't travel in the clipboard.
- The panel's footer lists what will paste badly (un-inlined fonts, inputs not inheriting the font). Fix until it is empty.

### Step 5 — Mark up components (§1 markup, rules R1–R8)
- `data-component` + `data-variant` on the root of every reusable piece; `data-layer` on its parts; `data-prop-text|swap|bool` on the layers the designer will edit; `data-icon` on icon SVGs.
- Ask which components get properties (R4) if the project hasn't decided (offer: all atoms · buttons and inputs only · none yet).
- Containers (nav bars, tab bars, tabs) follow R5 + R8: real auto layout, items named with `data-layer`.

### Step 6 — Verify (§5), then hand over
1. `SKILL_DIR/tools/check.sh path/to/index.html ./figma-check-out` → expect `errors 0`, auto-layout mismatches 0 (or known and explained), the variant-tree report reviewed.
2. Open the prototype in Chrome, open the panel, look at three screens, click **Copy design page**, and decode the real pasteboard (§5.4).
3. Give the person the paste steps, the pre-paste summary (counts, warnings), and say plainly what has and hasn't been pasted in real Figma.

## 0. Department rules (read before building screens)

Shared across the design department. If a technical default conflicts with a rule here, the rule wins and the conflict is reported to the designer. Items tagged **[Proposed]** are not built (§7); never tell a designer they work.

### 0.1 Pre-flight questions — ask before building or copying

| # | Question | Options | Sets |
|---|---|---|---|
| Q1 | How are the screens organised? | **By module** — follows the navbar: Module → Function → Screen, in navbar order · **By flow** — follows the requirements: Flow → Step, in the order the user moves through it | `organise`; registry order; section grouping; screen names |
| Q2 | Which positive and negative cases are in scope? | List the cases detected per module/flow (§0.3) and let the designer tick them | Which state screens get built; `case` tags |
| Q3 | How should it copy to Figma? | **Whole page** (recommended) · **Page + screen by screen** · **Page + by module/flow + screen by screen** · **Screen by screen only** (see the costs in §0.4) | `copy` |
| Q4 | Components or plain frames? | **Design page** (components, variants, instances) · **Plain copy** (frames only) | `output` |
| Q5 | Is there already a component library in the target Figma file? | No · Yes (name it) | Whether to match existing names (R6). Pastes always bring their own mains (§0.4) |

### 0.2 Component rules

**R1 — Content is per instance; variants are for state only.**
Anything that differs per placement — label text, icon, count, avatar image, link target — is **never** a variant value. Variants describe visual type, size and state only (`Type=Primary`, `Size=Medium`, `State=Hover/Active/Disabled`). A nav item "Members" with a users icon is an *instance* of `NavItem` with text and icon overrides, not a variant called `Members`.

**R2 — One layer tree per variant set.**
Every variant in a set has the same layers, with the same names, in the same order. A part one variant doesn't show (badge, chevron, trailing icon) is a **hidden layer** in that variant, not a missing layer. Figma keeps an instance's overrides on a variant swap only for layers it can match by name and position.
*Encoder (switch `unify`):* every variant main gets the superset of the set's top-level layers; the ones it doesn't show are hidden clones. Limits: top level only, at most 3 added layers per variant, containers and table rows excluded. Check: `node tools/figma-check/variants.js payload.html`.

**R3 — Stable, semantic layer names.**
Layers inside a component are named by role: `Icon`, `Label`, `Badge`, `Chevron`, `Leading`, `Trailing`, `Helper text`. Never by content (`Overview`, `icon / bell`) or by utility class (`stack-3`, `t-med`).
*Encoder (switch `names`):* role names inside main components. `data-layer="…"` in the markup always wins.

**R4 — Content is exposed as component properties.**
- **Text property** for every label the designer will edit (`Label`, `Helper text`).
- **Instance swap property** for every icon slot (`Icon`).
- **Boolean property** for every optional slot (`Show badge`, `Show icon`) instead of a `Content=…` variant.

*Encoder (switch `props`, confirmed in real Figma):* a layer gets a property only where the markup marks it: `data-prop-text="Label"` on the text, `data-prop-swap="Icon"` on the icon, `data-prop-bool="Show count"` on the optional part. Mark the layer inside the component, never the component's root. Every instance carries its own values, including nested instances. Not built: automatic marking; preferred values for instance swaps.

**R5 — Containers are one main component built from child components.**
`Sidebar`, `Topbar`, `TabBar`, `Tabs`, `Segmented` (config `containers`): the container is made of child instances (`NavItem`, `Tab`) that each carry their own `State`. The container gets variants only for real container-level states (`Collapsed/Expanded`, `Mobile/Desktop`), never for "which child is active".
- One main per container: its layers are the superset of every place it's used; slots a screen doesn't show are hidden. Name each slot with `data-layer` (`Members`, `Loyalty programme menu`, `Footer`).
- On a screen the container is an instance; per-screen state lives in nested overrides (variant swap on the child, text, show/hide).
- The container must be real auto layout: replace CSS margins (e.g. `margin-top:auto`) with a grow spacer or padding.
- *Encoder (switch `containers`):* up to 12 extra slots per container main.

**R6 — Components are for reusable items only.**
- Make a component when the item is an atom (button, input, chip, icon…) **or** repeats at least twice across the project.
- One-off blocks stay frames. Containers with free content (Card, Drawer, Dialog, Table shell, Page header, Form field) stay frames (config `frameOnly`); their inner controls are instances. Never componentise whole screens.
- Before creating a new set, check Universal Components and any existing library (Q5). The same thing under two names is a bug.
- Used in 2+ modules/flows → **Universal Components**. Used in one → beside that module/flow.

**R7 — Layout in context belongs to the screen, not to the main component.**
- How an instance is sized and placed — Fixed, Hug or Fill, alignment, position — comes from **that screen** and is set on the instance. The main never forces its sizing onto screens. *Encoder:* already true.
- Internal padding and gap belong to the component. When a component appears with different padding on different screens: a consistent pattern becomes a named variant property (`Density=Compact/Default`); a one-off is flagged to the designer (fix the HTML, add a variant, or keep it as a frame). *Encoder:* padding is part of the structural key, so a different padding creates a separate main — acceptable only if reported.
- Don't use per-instance padding overrides until a control sample shows Figma keeps them.

**R8 — Every item inside a container is its own component set.**
Each nav module, sub-menu entry and tab is **its own set** whose variants are states only; icon and label are built into that item's set (`NavItem / Members`, `Tab / History`), each with `State=Default / Active` (or `Group / Group Open`).
- Swapping `State` on an item never touches its icon, label or any other item. The icon is still a nested instance and can be swapped.
- Identity comes from `data-layer` (preferred) or the item's label text. Icon-only items stay in the shared set.
- This refines R1: content is still never a variant, but inside containers it lives in the item's own set.
- *Encoder (switches `identity`, `states`):* if an item never shows a state, the encoder copies the *style change* between two states of a sibling item (fill, border, effects, opacity, text style, icon colour, nested variant, swapped icon) onto it, keeping its own label, icon and size. Skipped when the sibling's states differ in structure.

### 0.3 Positive and negative cases

| Kind | Typical screens / states |
|---|---|
| Positive | Happy path, success confirmation, filled/edited state |
| Negative | Field validation errors, empty state, loading/skeleton, no permission, not found, server or network error, session expired, conflict, destructive-action confirm, partial success |

- Build only what the requirements state or clearly imply.
- If the requirements are silent but a case has **casualties** — money, data loss, permissions, irreversible actions, other users affected — **stop and ask**: *build the negative screen* · *note it on the flow only* · *out of scope*.
- Tag every screen `case: 'positive' | 'negative'`. The tag shows in the panel and in the Figma frame name.
- Project rules can add to this (e.g. admin portals: every submit ends in a success state).

### 0.4 Copy granularity — what each option costs
Figma can't link a paste to components already in the file: every paste with components brings its own mains (`publishedAssetGuids` is empty).

| Q3 option | Pastes | Components | Use for |
|---|---|---|---|
| **Whole page** (`copy: ['page']`) | 1 | One set of mains, everything linked | **The hand-off file.** Default |
| Page + screen by screen (`['page','screen']`) | Page once, then single screens | Page linked; single screens are plain frames for patching | Hand-off plus later fixes |
| + by module/flow (`['page','group','screen']`) | 1 per module/flow | Plain frames by default (`groupCopy: 'plain'`); `'design'` duplicates shared mains per paste | Reviewing one area |
| Screen by screen only (`['screen']`) | 1 per screen | Plain frames | Quick checks |

To remove duplicate mains after split design pastes: swap each instance to the file's component, delete the extra mains. **[Proposed]** paste Universal Components once and link later pastes to them (§7, 11.7).

## 1. Prototype contract

**Registry** (global `const` or `window.` properties, defined before the engine):
```js
const MODULES = [{ key: 'members', name: 'Members', note: 'SRS-101' }];             // navbar order; needed for organise 'module'
const FLOWS = { '4.1': { name: 'Find a member', module: 'members', note: 'SRS-101' } }; // needed for organise 'flow'
const SCREENS = [
  { id: 'M1', module: 'members', fn: 'Member list', screen: 'Member list', state: 'Loaded', case: 'positive', render: () => html },
  { id: 'M2', module: 'members', fn: 'Member list', screen: 'Member list', state: 'No results', case: 'negative', template: '#scr-m2' },
  { id: '4.1a', flow: '4.1', title: 'Member list', case: 'positive', render: memberList },
];
```
- `id` unique; `title` = `screen — state` when not given. `render()` returns HTML, or `template` points at a `<template>`.
- Group key = `module` (organise 'module') or `flow` (organise 'flow'). Groups follow `MODULES` order (module) or first appearance in `SCREENS` (flow), so order `SCREENS` the way Q1 says. In flow mode, flows with a `module` get module headings in the panel.
- Figma frame name (default): `<Module or Flow> / <Function> / <Screen — State> · Positive|Negative`, e.g. `Members / Member list / Member list — No results · Negative`. Section name = module/flow name. Override with config `screenName` / `sectionName`.
- Each screen's root element should have the screen's real size (e.g. `width:1440px; min-height:900px`, or `width:390px; height:844px`). `frameWidth` is the width of the hidden render host.

**Markup:**
- **Components**: `data-component="Button" data-variant="primary/md/default"` on the root of every reusable piece. Helper: `const dc = (name, variant) => \` data-component="${name}"${variant ? \` data-variant="${variant}"\` : ''}\``. Keep `data-variant` complete everywhere (all segments), in the order of `variantProps[name]`.
- **Parts and properties**: `data-layer="Icon|Label|Badge|Chevron"`, `data-prop-text="Label"`, `data-prop-swap="Icon"`, `data-prop-bool="Show badge"`, on the layer inside the component (the text span, the icon `<svg>`, the optional badge), never on the root. `data-prop-text` must land on a text layer, `data-prop-swap` on a nested component or icon; anything else is ignored with a console warning. Loose text that needs a property gets its own `<span>`. No Text property on rich text (`<b>` runs). Keep a slot's markup identical everywhere the component is used (it is part of the structural key).
- **Icons**: inline `<svg data-icon="bell" …>` (Lucide-style strokes are fine).
- **Fonts**: base64 TTF `@font-face`; `font-family: inherit` on form controls (Step 4).
- **Images**: `data:` URLs or local files.
- **Layout**: flexbox wherever possible — flex containers become auto layout. Avoid margins between flex children (use `gap`), `margin-top:auto` (use a grow spacer), and wrap.

## 3. What the encoder does (summary)
Each screen is rendered off-screen and read back from the DOM: flex containers become auto layout (only when the geometry proves it), text keeps exact fonts and styled runs with a glyph cache, SVGs become vector networks, images travel as bytes. In design-page mode, every allowed `data-component` and `data-icon` becomes a main component (first occurrence, nested first), identical structures share one main, variants are named from `data-variant`, optional parts merge into hidden layers, containers become one main built from item sets, and every occurrence on a screen becomes an instance with overrides and property values. Details, the clipboard format and the pitfalls list: `references/engine-internals.md`.

## 4. Switches
Each behaviour can be turned off per browser without editing code, to isolate a regression in one paste round: panel → **Figma switches**, or localStorage `<storageKey>-fig-<name>` = `'0'` (`hug`, `merge`, `names`, `unify`, `containers`, `identity`, `states`, `props`, `derived`, `dsd`). Off by default (`'1'` = on): `props-only`, `sidebar-frame`.

## 5. Verify without Figma (all of it before handing over)
1. **Headless payload + checks**: `SKILL_DIR/tools/check.sh prototype.html outdir [page|group:<key>|screen:<id>]`. It decodes the payload with the schema inside it (orphans, zero sizes, blob ranges, colours, duplicate position keys), re-simulates every auto-layout child position and every Hug size (`render2.js`, instances resolved), and reports variant sets that don't share one layer tree. Target: 0 errors, 0 unexplained mismatches.
2. **Look at it**: open `outdir/payload.svg` (re-render of the decoded payload) next to the HTML screen in headless Chrome. Check fonts, icons, images, spacing.
3. **Panel preflight**: the warning box in the panel footer is empty (fonts inlined, controls inherit the font).
4. **Real pasteboard**: click Copy in a real Chrome, then `SKILL_DIR/tools/figma-check/grab.sh pb.html` (or `osascript -e 'the clipboard as «class HTML»' | sed -E 's/^«data HTML//; s/»$//' | xxd -r -p > pb.html`) and `node SKILL_DIR/tools/figma-check/validate.js pb.html`. This proves the markers survive the clipboard.
5. **Paste ladder for a new project or after a Figma release** (paste each, report the last that worked). In the browser console: `figmaTest('0')` real Figma sample (control) · `'A'` frames + auto layout · `'B'` text without glyphs · `'C'` text with glyphs · `'D'` icons · `'E'` image · `'0c'` real instance sample · `'0s'` real variant-set sample. If `0` fails, Figma changed its format; if `0` works and `A` fails, the encoder is wrong.
6. **Best source of truth for a new feature**: ask the designer to build the structure in Figma, select it and ⌘C; save it with `grab.sh sample.html` and diff field shapes against the encoder's output (`decode.js` reads Figma's zstd payloads, Node 22.15+).
7. **Hand tests to designers without the console**: build the payload yourself and put it straight on the Mac clipboard: `osascript -e "set the clipboard to «data HTML$(xxd -p payload.html | tr -d '\n')»"`. The designer only clicks the canvas and presses ⌘V. Warn them that copying anything else first replaces it. Give the checklist as plain steps ("select Row 3, change Label in the right panel: does the canvas change?").

Report only the checks that ran. A payload that decodes is not a confirmed paste.

**Platforms:** `check.sh` runs on macOS and Linux (bash, Node 18+, Chrome or Chromium; set `CHROME=/path` if it isn't found; `npm install` in `tools/figma-check` needs network once). `grab.sh` and the `osascript` steps (4, 7) are macOS-only. Where they can't run (e.g. a sandbox with no clipboard), stop at steps 1–3 and tell the person the clipboard and Figma paste are unverified.

## 6. Known limits
- Static HTML prototypes only (no React/Vite render path). Chrome only (copy event + user activation, about 5 s).
- Fill is expressed through `grow`/`stretch` only; Hug is detected; fixed CSS widths stay fixed.
- Merged mains carry the bigger structure: a text-only button is an instance of `Content=Icon + Text` with the icon hidden. Mark the icon `data-prop-bool="Show icon"` to make it a Boolean property.
- Structural alternates deeper than the top level stay as `Content=…` variants; unify works on the top level only, max 3 added layers.
- CSS gradients, filters and per-side dashed borders are approximated or dropped. No variables or styles binding yet (colours are raw).
- Same-name siblings (repeated `Nav Item`) rely on Figma matching them by order (not verified).
- Padding/gap is part of the structural key (R7). Split design pastes duplicate mains (§0.4).
- Text in families without an inline TTF pastes without a glyph cache: correct in Figma only if the font is installed there.

## Motion → Figma plugin (in `assets/motion-plugin/`)

Also by Sebastian: a Figma plugin ("Motion Handoff Builder") that turns an animation export into one Figma frame with native Figma Motion keyframes. Import it once in the Figma desktop app (Plugins › Development › Import plugin from manifest…, pick `assets/motion-plugin/manifest.json`), then drop the export folder in. It reads three formats, detected by content: a baked handoff bundle (`kind: "hyperframes-handoff"`, full quality), a raw HyperFrames export (draft quality, converted in the plugin) and a variants file (poses as components). The bake step that makes the full-quality bundle (`handoff/bake.mjs`) is not in this folder yet.
